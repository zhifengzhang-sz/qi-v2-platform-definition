# Visualization: the research behind its spec

This file covers what is known that bears on what visualization must guarantee: how a page gets what a log holds, how a bar still forming is shown, how results given again are shown, and what "the chart shows exactly the records of the topics it reads" can be checked as. `docs/designs/spec.md` (Visualization, and the last theorem of The working space) states what the component must do.

Sources are marked by how each was read: [READ] read in full at the part cited; [SUMMARY] from a search or fetch summary only; [INFER] an inference, not stated by a source.

What the definition holds, for all four issues [READ, `lean/`]: `structure Visualization` has one field, `chart : Process (Visualization.In Model) (Visualization.Out Model)`, with `In := Kafka.Partition Market.KLine × (Model → Kafka.Partition MarketModelEngine.Result)` and `Out := Log Market.KLine × (Model → Log MarketModelEngine.Result)` (`lean/Visualization.lean`). The wiring's theorems `Wiring.visualization_chart` and `Wiring.chart_without_engine` say which topics `chart` is applied to, not what its logs hold (`lean/Wiring.lean`). `Visualization.Spec`, the structure the spec names for visualization's requirements, is not in `lean/`: its one requirement, `chart`, is stated by the spec alone.

## 1. From a log to a page: how does a browser get each topic from its start and then live, with no record missed and none twice?

**Kind:** engineering. **Bears on:** `chart` ("for each topic it reads, its log is the values of that topic's records that have one, in order") and "The chart on the page at any moment is the set of what its logs hold so far" (Visualization); "that each reader reads it from its start, that retention removes no record before it is read" (Order).

A record's place is its offset, and a reader's place is one number per partition. "Kafka maintains a numerical offset for each record in a partition. This offset acts as a unique identifier of a record within that partition, and also denotes the position of the consumer in the partition." "The position of the consumer gives the offset of the next record that will be given out. It will be one larger than the highest offset the consumer has seen in that partition." "Note that offsets are not guaranteed to be consecutive (such as compacted topic or when records have been produced using transactions)." Apache Kafka 4.1, `KafkaConsumer` Javadoc, Offsets and Consumer Position, https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html [READ].

The reader sets its own position, in either direction. "Kafka allows the consumer to manually control its position, moving forward or backwards in a partition at will." "Special methods for seeking to the earliest and latest offset the server maintains are also available (`seekToBeginning(Collection)` and `seekToEnd(Collection)` respectively)." `seekToBeginning`: "Seek to the first offset for each of the given partitions." A reader that keeps its own position needs no group: "Each record comes with its own offset, so to manage your own offset you just need to do the following": "Configure enable.auto.commit=false", "Use the offset provided with each ConsumerRecord to save your position", "On restart restore the position of the consumer using seek(TopicPartition, long)". `endOffsets` gives a partition's end offset, and "does not change the current consumer position of the partitions." `KafkaConsumer` Javadoc, Controlling The Consumer's Position, Storing Offsets Outside Kafka, `seekToBeginning`, `endOffsets`, as above [READ].

"The first offset" is the earliest the server still holds, not the first ever written: "seek(0) is equivalent to seekToBeginning for a TopicPartition with beginning offset 0, assuming that there is a record at offset 0 still available." `KafkaConsumer` Javadoc, `seek`, as above [READ]. So a read from the beginning is a read of the whole log only where nothing has been removed, which `lean/Kafka.lean` takes as given: "That a reader reads the whole log is assumed here, not proved: it holds where retention and compaction remove no record before the reader has read it." [READ]

A reader that does not seek, and has no stored offset, starts at the end by default. `auto.offset.reset`: "What to do when there is no initial offset in Kafka or if the current offset does not exist any more on the server (e.g. because that data has been deleted)": "earliest: automatically reset the offset to the earliest offset", "latest: automatically reset the offset to the latest offset", "none: throw exception to the consumer if no previous offset is found for the consumer's group"; default `latest`. Apache Kafka 4.1, Consumer Configs, https://kafka.apache.org/41/configuration/consumer-configs/ [READ]. The same setting decides a seek outside what the log holds: "If this is set to "earliest", the next poll will return records from the starting offset. If it is set to "latest", it will seek to the last offset (similar to seekToEnd()). If it is set to "none", an OffsetOutOfRangeException will be thrown." `KafkaConsumer` Javadoc, `seek`, as above [READ]. So the setting acts only where there is no offset or one out of range: a resumption from, or a seek to, an offset whose records were removed moves without an error under `earliest` or `latest`, and is an error under `none`; a read begun by `seekToBeginning` starts at the earliest offset still held under every setting, and shows no sign of what was removed before it. [INFER]

Applying a record twice is harmless where the record says where it goes. Reading, processing, then saving the position gives at-least-once: "when the new process takes over the first few messages it receives will already have been processed"; "In many cases messages have a primary key and so the updates are idempotent (receiving the same message twice just overwrites a record with another copy of itself)"; the general way to exactly-once into another system is "letting the consumer store its offset in the same place as its output". Apache Kafka 4.1, Design, Message Delivery Semantics, https://kafka.apache.org/41/design/design/ [READ]. For a page, the output is the chart's model: a position kept with the model, and moved with it, is that pattern. [INFER]

Server-sent events carry one resumption string per connection, kept by the browser. The `id` field: "If the field value does not contain U+0000 NULL, then set the last event ID buffer to the field value." On dispatch: "Set the last event ID string of the event source to the value of the last event ID buffer. The buffer does not get reset, so the last event ID string of the event source remains set to this value until the next time it is set by the server." An event cut off is not given and does not move the string: "If the file ends in the middle of an event, before the final empty line, the incomplete event is not dispatched." On reconnecting, "If the `EventSource` object's last event ID string is not the empty string", the user agent sets `Last-Event-ID` to it in the request; "The `Last-Event-ID` HTTP request header reports an `EventSource` object's last event ID string to the server when the user agent is to reestablish the connection." WHATWG HTML Living Standard, 9.2 Server-sent events (9.2.1 to 9.2.10), https://html.spec.whatwg.org/multipage/server-sent-events.html [READ].

What the standard leaves out [READ, same section, by its absence]: what a server does with `Last-Event-ID`; any meaning of the string (the value space is "essentially any UTF-8 encoded string"); a way for a script to set it (the constructor takes a URL and `withCredentials` alone, and the string "must initially be the empty string"). So a new page starts with no position, a position for a first connection travels in the URL, and one string stands for the whole connection. [INFER]

WebSocket has no position, no replay and no resumption. "It is expected that metadata would be layered on top of WebSocket by the application layer, in the same way that metadata is layered on top of TCP by the application layer (e.g., HTTP)"; "Other than that, WebSocket adds nothing." A frame carries no sequence number and no message identifier, and of a lost connection the protocol says only when to try again (7.2.3). RFC 6455, The WebSocket Protocol, https://www.rfc-editor.org/rfc/rfc6455 [READ: sections 1.5 and 5 to 7 in full, the rest by a search of its words]. The browser's interface does not reconnect either: when the connection is closed the user agent must "Change the ready state to CLOSED (3)" and "Fire an event named close". WHATWG WebSockets Living Standard, https://websockets.spec.whatwg.org/ [READ: the close steps in full, the rest by a search of its words].

What follows for a page, whatever carries the records. [INFER]
- A browser script speaks HTTP and WebSocket, not Kafka's protocol, so a reader of the topic stands between the topic and the page, and what the page holds is what that reader passed on.
- Each record reaches the page with its topic's offset, and the page keeps one position for each topic it reads: "Kafka keeps order within a partition only" (`Kafka.Topic.Logs`, `lean/Kafka.lean`), so one position cannot stand for two topics, and a resumption string for a connection carrying both holds both positions.
- A new page reads from the topic's first offset; a page that reconnects reads from the offset after its last. The same order of offsets runs from history into live: the end offset read at the start only says where catching up ends.
- The page takes a record whose offset is not above its position as already had, so a resend changes nothing.
- A gap in offsets is not a missed record (offsets may skip, and a record with no value takes an offset and gives no item). On the clean topic a missed record is seen in the k-lines themselves: each holds its place as its `index` (`cleaner`, `publishClean`), so the k-lines read are those of `index` 0 to n − 1. A result does not hold its place in its topic (a merged bar's `mIndex` numbers the bar, not the record): on the engine's topic nothing in the records shows a miss.

**The options.**
- Resumption by the page's position, sent on reconnecting (the `id` and `Last-Event-ID` pattern, or the same carried by the application over WebSocket): the log is the replay and nothing is kept for a page; needs a reader that starts at any offset, one per connection.
- A full read from the first offset on every connection: no position to hand over; costs the whole history again at each reconnection, and the page must still pass over what it has.
- History by one path and live by another (a snapshot, then a stream from the snapshot's end offset): a faster first load; costs a second path that must give the same records as the log, and a boundary where a record can be lost or doubled unless both sides name the same offset.

**What it gives the spec.** `chart` holds of a page only under three conditions, which the spec can state as what is verified of what is built, beside the Order table's "each reader reads it from its start": (1) the read of each topic starts at its first record and no record was removed before it was read, an assumption about running that a read from the beginning cannot check under any setting of `auto.offset.reset` (on the clean topic the first k-line's `index`, 0 or not, shows it [INFER]), while for a resumption from a removed offset `none` makes the loss an error where `earliest` and `latest` hide it; (2) each record reaches the page with its topic's offset and a reconnection resumes by offset, one for each topic; (3) applying a record is idempotent by offset. "At any moment" needs no more: while the page catches up, its chart is the set of a prefix, as `chart` is of what has been read so far [INFER]. Left as choices: the transport; whether the position is kept by the page or for it; whether history comes by the path live does.

**Gaps.** No standard says what a server does with `Last-Event-ID`. Kafka's protocol guide was not read: that a browser script cannot speak it is an inference. No source on a reader placed between a topic and a browser was read.

## 2. The live candle: what does a chart need to show a bar still forming, and what carries it?

**Kind:** modelling. **Bears on:** "Market's `OngoingKLine` is held with its contract and carried by no topic ... and the chart shows none" (The contract specs); "a k-line by its `index` and `date`" (Visualization, Features).

The definition has the record and no place for it. `Market.OngoingKLine` holds `index` ("the place it will take in its series when complete, from 0: a position"), `date` ("its begin time: milliseconds since 1970-01-01 00:00:00 UTC"), `open`, `high`, `low`, `close`, `volume` and `asOf` ("when its values were last updated: milliseconds since 1970-01-01 00:00:00 UTC"). Its rules are its k-line's (`finite`, `range`, `volumeNotNegative`, of `OngoingKLine.kline`) and `asOfNotBeforeDate` (`o.date ≤ o.asOf`). No rule relates two ongoing k-lines of one `index`, or an ongoing k-line to the complete one. `lean/Contract/Market.lean` [READ]. `Visualization.In` has no input of `OngoingKLine`, and each of acquisition's topics is a `Kafka.Partition Market.KLine`. `lean/Visualization.lean`, `lean/Acquisition.lean` [READ]. The clean series' dates ascend and each k-line's `index` is its position (`cleaner`), so on the chart the clean topic only ever adds a bar after the last. [INFER from the spec's `cleaner`]

How an exchange gives a forming bar. One stream carries the bar while it forms and when it closes: "The Kline/Candlestick Stream push updates to the current klines/candlestick every second", each message with the bar's start time (`"t"`, "Kline start time"), the event's time (`"E"`, "Event time"), the values so far and a flag (`"x"`, "Is this kline closed?"). Binance Spot API, WebSocket Streams, Kline/Candlestick Streams for UTC, https://github.com/binance/binance-spot-api-docs/blob/master/web-socket-streams.md [READ]. Its begin time is `OngoingKLine.date` and its event time `asOf`; `OngoingKLine` has no closed flag, the closed bar being a `KLine`. [INFER]

How a chart library shows one. `update(bar, historicalUpdate?)`: "Adds new data item to the existing set (or updates the latest item if times of the passed/latest items are equal)"; "Time of the new item must be greater or equal to the latest existing time point. If the new item's time is equal to the last existing item's time, then the existing item is replaced with the new one." `setData`: "Ordered (earlier time point goes first) array of data items. Old data is fully replaced with the new one." Lightweight Charts documentation, `ISeriesApi`, https://tradingview.github.io/lightweight-charts/docs/api/interfaces/ISeriesApi [READ]; the documentation is of version 5.3 and the source is cited at the tag v5.2.1 throughout, where these doc comments have the same words, https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/api/iseries-api.ts [READ]. An earlier time is refused by an error, "Cannot update oldest data, last time=${lastSeriesTime}, new time=${time}". https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/data-layer.ts, `updateSeriesData` [READ]. The library's real-time demo sends a forming candle as the same `time` again with new values, then a later `time` for the next one. https://github.com/tradingview/lightweight-charts/blob/v5.2.1/website/tutorials/demos/realtime-updates.js [READ].

So a chart's two operations on its k-lines are append (a later begin time) and replace the last (the same begin time), and the forming bar is the last candle, replaced by its begin time. [READ for the operations; INFER for the match with `OngoingKLine.date`]

What a forming bar on the chart needs that the definition does not hold. [INFER]
- A log to be in: every update of a forming bar is a record, appended and kept, since a topic is its whole log, never compacted (`Kafka.compaction_not_process`). The chart's set then holds every update of every bar, and the one candle drawn is a view of them.
- A rule for which update stands: of the ongoing k-lines of one `index`, the one of the latest `asOf`, or the last in the log. By `asOf` the rule reads from the set, without the log's order, but only with a second rule to state, that a later update of an `index` has a later `asOf`: none says so (`asOfNotBeforeDate` relates `asOf` to the same record's `date`), and two updates of one `asOf` leave the latest undefined.
- A rule for the end: the clean `KLine` of `index` n stands in place of every ongoing k-line of `index` at most n. A forming bar the cleaner later drops (it breaks market's rules, or its date is not after the last kept) never gets a clean k-line of its `index`: the next clean k-line takes that `index`, with a later `date`, and the rule by `index` still removes it. Which series its `index` counts in (the clean one, for a chart of the clean series) has to be said.
- A statement on the engine: it reads the clean topic alone, so it works on no forming bar whether or not the chart shows one.

**The options.**
- No forming bar, as the spec stands: the chart's k-lines are the clean topic's, append only; costs the live candle (the newest candle shows once its period has ended and its bar is published).
- A fourth kind, a topic of `OngoingKLine` written by acquisition and read by visualization: the chart stays a function of logs; costs a kind and a topic, an input of `Visualization.In` and a log of `Visualization.Out`, a requirement on acquisition (its source gives forming bars), the two rules above, and a log that grows with every update of every bar.
- A forming bar sent to the page beside the topics: no new topic; the chart then shows a record that is in no log it reads, against "the chart shows exactly the records of the topics it reads".
- A forming bar the page makes from trades: needs a topic of trades and a record for a trade, which market's contract does not have, and puts the making of a bar in the page.

**What it gives the spec.** As it stands, "the chart shows none" needs nothing more, and the chart's only operation on k-lines is append. If the live candle is wanted, it is a change to what acquisition publishes and to visualization's input, with two rules that relate records (latest `asOf` of an `index`; the clean k-line over the ongoing ones), which the contract's rules, each of one record alone, do not give: they would be the component's.

**Gaps.** One exchange's documentation was read; no source on when a bar is closed across vendors, or on trades reported after a bar's close.

## 3. Showing results that are given again: what must a chart do to show exactly what the topic holds?

**Kind:** modelling. **Bears on:** "Which record still going on it draws over which is the page's" (Visualization, Features); "when it gives again a record still going on are the worker's library's" and `covers` ("one still merging, its `confirmEnd` not set, at the least") (the engine).

No result names what it replaces. `MarketModelEngine.Result` is an inductive of six cases (`mergedBar`, `fractal`, `line`, `segment`, `move`, `consolidation`), each holding one of chanlun's records and nothing else: no identifier of the result, no number in the topic, no field naming an earlier record, and no case that takes a record back. `lean/MarketModelEngine.lean` [READ]. The records: `MergedBar` has `mIndex` ("its number: a bar"), `up`, `start`, `end`, `confirmEnd` ("not set while it is still merging"), `extremes`, `index`, `high`, `low`; `Fractal` has `mIndex` alone; `Line` has `start`, `end`, `confirmEnd`; `Segment` and `Move` add `level`; `Consolidation` has `level`, `start`, `end`, `confirmEnd`, `zg`, `zd`, `gg`, `dd`. "A `confirmEnd` not set means the record is still going on". Every rule is "of one record alone", and "how records are gathered: a run of them, their order, and which is still going on are their user's". `lean/Contract/Chanlun.lean` [READ]. So nothing in the definition says that two merged bars of one `mIndex` are one bar given twice, that a line given again keeps its `start`, or that a record with `confirmEnd` set is never given again; and a `Fractal`, having no `confirmEnd`, does not say whether it is still going on. [READ for the absence; the three examples are INFER]

A record given again is a second record, and both stay. The engine's topic holds its results in its worker's order (`publish`), `covers` asks that each k-line read be within a merged bar among its results, one still merging at the least, and the engine's features speak of when the worker "gives again a record still going on". `docs/designs/spec.md`, The market model engine [READ]. So a bar that grows is given more than once. [INFER] A topic is its whole log: "No view that replaces a record already given is a process of the log" (`Kafka.compaction_not_process`). `lean/Kafka.lean` [READ]. The chart's set is ordered by inclusion and a process is monotone, so a row once in it stays; and it is a set: "A row is in it or not: put there twice, it is there once" (`Kahn.Rows`). `lean/Kahn/Rows.lean` [READ]. So the set of what the logs hold has the record and each later giving of it that differs, and has an identical repeat once; showing the later in place of the earlier is a view of the logs, not a process. [INFER] The spec leaves which is drawn over which to the page.

A set does not say which giving is the later. `Rows.ofLogs` forgets order; `Visualization.Out` is logs, which keep it. A rule "the last of those of one key stands" reads the log, not the set, unless a field orders the givings; no field of a result is stated to. [INFER]

What a keyed log gives, in Kafka's own terms. "Log compaction ensures that Kafka will always retain at least the last known value for each message key within the log of data for a single topic partition"; "Any consumer progressing from the start of the log will see at least the final state of all records in the order they were written"; and taking a key back is a record of its own: "A message with a key and a null payload will be treated as a delete from the log." Kafka Design, Log Compaction, as in 1 [READ]. The reading of a log as a table by key therefore rests on a key in each record and on a record that deletes; the working space's topics have no key (`Kafka.Topic.ofName`, `Key := Empty`) and its logs pass over a record with no value. [READ for both; the comparison is INFER]

What a chart library gives for revision. A series refuses an earlier time (issue 2); `historicalUpdate` "allows updating an existing data point that is not the latest bar", one point at a time, and fails where there is none ("Cannot update non-existing data point when historicalUpdate is true"). `ISeriesApi` documentation and `data-layer.ts`, as in 2 [READ]. A drawing over the series keeps its own items and replaces them itself: markers are set as a whole list (`setMarkers`), and a drawing is told of a data change only its extent, `DataChangedScope = 'full' | 'update'`, never which bar. https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/plugins/series-markers/wrapper.ts and `iseries-api.ts`, as in 2 [READ]. So the library has no notion of a result that replaces a result: what stands is decided before the library is given anything. [INFER]

**The options.**
- Every record drawn: the chart is the set and needs no rule; a line still going on is drawn at each end it was given with, and reads as several lines.
- The page's own rule, as the spec stands: costs nothing in the definition; two pages of one topic may draw different charts, and what is drawn is checked against nothing stated.
- A stated key, the last giving in the log standing (a merged bar by `mIndex`; a line by `start`; a 线段, a 走势 and a 中枢 by `level` and `start`, say): the view is a function of the log; costs a requirement on the engine that a record given again keeps its key, narrowing "when it gives again a record still going on are the worker's library's", and it does not cover a record still going on that ceases with no later giving of its key.
- At most one record still going on of a kind and level: a later one with `confirmEnd` not set stands in place of every earlier one of that kind and level; needs no key and covers a record that ceases; costs the same kind of requirement on the engine, and whether the library works so is not known.
- A result that names what it replaces, or a seventh case that takes a record back: exact; costs a change to `Result`, which is the platform's message, not the contract's.
- A confirmed boundary: a record with `confirmEnd` set is final and drawn once; costs a requirement that such a record is never given again differently, and leaves the records still going on to one of the rules above.

**What it gives the spec.** The feature "Which record still going on it draws over which is the page's" rests on nothing in the records: no result names what it replaces and no rule relates two records. To say more than "the page's", the spec either states that every record is drawn, which asks nothing of the engine, or takes one of three: a stated key, at most one record still going on of a kind and level, or a result that names what it replaces, each a requirement on the engine or a change to its message. The confirmed boundary settles the confirmed records alone and is taken with one of those. The choice is left. Whatever is chosen, the view is stated as a function of the logs, their order included, not of the set.

**Gaps.** How the worker's library gives a record again (which fields stay fixed while a record is still going on, whether one can cease, whether a confirmed record is ever given again) is stated by no source read here.

## 4. What can "the chart shows exactly the records of the topics it reads" be checked as?

**Kind:** modelling. **Bears on:** the last theorem of The working space; `chart` (Visualization); `Kahn.Rows.ofLogs`.

The claim is not yet a theorem of `lean/`: the spec states it, with no name, as the last of the wiring's theorems, and `lean/Wiring.lean` holds of visualization only `visualization_chart` and `chart_without_engine`. [READ] It can be had from one theorem the definition holds and the requirement `chart`, which it does not. [INFER] The theorem is `Kahn.Rows.has_ofLogs`: `(ofLogs s).has ⟨i, a⟩ ↔ ∃ n, (s i).get n = some a`, "The set holds a message of log `i` exactly when log `i` holds it, at some position". `lean/Kahn/Rows.lean` [READ]. With `chart` (each log is the values of its topic's records that have one, in order), a row is in the chart's set exactly when a record of that topic read so far has that value. [INFER] Two limits of "exactly the records" follow from the types: it is the records' values (their timestamps, headers and offsets are in no log of `Visualization.Out`), and two records of one value are one row. On the clean topic no two k-lines have one `index`, so nothing is lost; on the engine's topic a result given twice alike is there once. [INFER]

What the set does not order. Visualization gives one log for each topic, and no process puts two logs in one by arrival (`Kahn.no_arrival_merge`). `refers` says a result's k-lines are in the clean series the engine has read, not that the page has read them: a page may hold a result before the k-lines it names. [READ for the two statements; INFER for the consequence] So the set holds the result at once, and "each record placed by its own positions" can be done only once those positions are read: holding is `chart`'s, placing waits.

What is built can be checked on the page's model, as a function of the prefixes read. The checks. [INFER]
- Sound: every item of the model is the value of a record of a topic it read, at a known offset; no item has another source.
- Complete: every record read that has a value gives an item; where the view leaves a record undrawn (issue 3), the rule that says so is the stated one.
- Independent of how it arrived: the model after the first n records of each topic is the same whether they came at once, one at a time, across a reconnection, or with a resend; and the same for any interleaving of the two topics.
- K-lines in order: the model's k-lines are those of `index` 0 to n − 1, their dates ascending.

What a library lets a check read back. `data()`: "Returns all the bar data for the series. The returned items are copies rebuilt from the series' internal data, not the objects passed to `setData` or `update`. Whitespace items are excluded. For built-in series types each item contains only the fields the series supports; any other fields are dropped." `ISeriesApi` documentation, as in 2 [READ]. So the bars a series holds can be compared with the log's k-lines by time and the four prices; `index` and `volume` are not among a candlestick's fields, and are checked on the page's own model. [INFER] The library's order check on `setData` ("data must be asc ordered by time") is skipped in a production build, where `update`'s refusal of an earlier time is not: the order of what is handed over is the page's to hold. https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/data-validators.ts and `data-layer.ts`, as in 2 [READ].

The pixels are outside the claim. The library tests its own drawing by comparing screenshots of two builds of itself, the last known good one and the one under test. https://github.com/tradingview/lightweight-charts/blob/v5.2.1/tests/e2e/graphics/README.md [READ]. A drawing is thus checked against an earlier drawing, not against its data; no source states the correctness of a drawn chart against its data. [INFER] The claim stops at the data handed to what draws; the spec leaves "how" to the page.

**What it gives the spec.** The theorem, once `chart` is in the definition, can be proved as `has_ofLogs` applied to the logs `chart` gives [INFER]: it holds of the set of values, and says nothing of what is drawn. Of what is built, the spec can ask the four checks above on the page's model. Left as a choice: whether the drawn view (which giving of a result stands, issue 3; which update of a forming bar, issue 2) is stated as a second function of the logs, and so checked the same way, or stays the page's and unchecked.

**Gaps.** No paper or standard on checking a chart's content against its data was found. Only one library's read-back and tests were read.
