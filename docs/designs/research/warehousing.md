# Warehousing: the research behind its spec

This file covers the algorithmic and engineering issues behind warehousing: whether the store is a copy of the log, what delivery gives and what makes a sink idempotent, how corrections are kept, and how a table is replayed and says what it covers. `docs/designs/spec.md` (section "Warehousing", and the row of the Order table on the order of what is published) states what the component must do. Of the definition, `lean/` holds `Warehousing` (its `consumer`, `run`, `run_apply`), `Wiring.table`, `Wiring.warehousing_pushes`, `Wiring.table_rows`, `Workspace.tableRows`, `Workspace.has_tableRows`, `Kahn.Rows`, `Kahn.Rows.ofLogs`, `Kafka.Record`, `Kafka.Topic` and `Kafka.Partition`. It holds no `Warehousing.Spec`, no `Acquisition.Spec` and no `Log.filterMap`, which the spec names: `Warehousing.consumer` is any process of `Log (Kafka.Record K V)` to `Log V`, and each part of `Acquisition` any process of its type ("What a part gives is the implementation's", `lean/Acquisition.lean`). So where this file rests a claim on `consumer`, `reader`, `cleaner` or `publish…`, it rests on the spec's text, not on a theorem.

Sources are marked by how each was read: [READ] read in full at the part cited; [SUMMARY] from a search or fetch summary only; [INFER] an inference, not stated by a source. Each web source marked [READ] was read as the page's own text (a PDF as its extracted text). The options of each section are inferences from what it cites.

## 1. Is the store a copy of the log, and when does replay reproduce it?

**Kind:** modelling and engineering. **Bears on:** "Keep in the database every record of acquisition's topics, of every kind" (Warehousing, Objectives); "A table is a set of rows, each a pushed value marked with the log it is from, in no order" (Features).

The definition. A table is a process of the input logs: `Workspace.tableRows name : Process W.Inputs (Rows (W.TableRow name))`, which is `Rows.ofLogs` of the logs warehousing pushes into the table named `name`. `Workspace.has_tableRows`: "A table holds a row exactly when the log it is from holds its message, at some position." `Wiring.table_rows`: the table named `name` holds, of the rows from acquisition's topic of kind `κ` pushed into it (`S.table κ = name`), "exactly the k-lines the consumer pushes for that topic, in no order", the consumer being `S.warehousing.consumer Empty Market.KLine` on that topic's one partition. `Rows` is ordered by inclusion, and `Rows.has_sup`: "The limit of a growing set holds a row once some stage holds it." That a table is a set of rows "is a modelling choice, not a theorem, and so is what a row is" (`lean/Workspace.lean`). [READ: `lean/Workspace.lean`, `lean/Wiring.lean`, `lean/Kahn/Rows.lean`] So a table is a function of the logs; a row once held is held at every later stage, a process being monotone; the model has no update in place, no delete, and no writer but the logs. [INFER] `table_rows` says the table holds what the consumer pushes, whatever the consumer is; that this is every value of the topic is the spec's requirement `consumer`. [INFER]

A log kept whole reproduces every state made from it. "If we had infinite log retention, and we logged each change in the above cases, then we would have captured the state of the system at each time from when it first began. Using this complete log, we could restore to any point in time by replaying the first N records in the log." With retention, "the log is no longer a way to restore the current state–now restoring from the beginning of the log no longer recreates the current state as old updates may not be captured at all." [READ: Apache Kafka 4.1 documentation, Design, Log Compaction, https://kafka.apache.org/41/design/design/]

Replay holds only while the log is the one source of change. In kdb+tick the tickerplant "logs every single message it receives to a binary log file. In the event of a subscriber process failing, this log file can be used to restore any missing data"; "tickerplant does not playback the log file. An individual client of the tickerplant (e.g. a RDB) replays the log file when required"; the subscriber's `upd` is `insert`, so "executing a single line in the logfile is equivalent to" ``insert[`tablename;tabledata]``. The paper's failure: "manual user actions that are not recorded in the TP log can cause errors when replaying". A row is inserted through the tickerplant, deleted in memory "without publishing to the TP", and inserted again; the log holds two inserts, and on replay "the kdb+ process tries to perform an insert to a keyed table, but there is a restriction that the same key cannot be inserted in the table twice. The delete that was performed manually between these two steps was omitted." Its rule: "All operations on this table should be made via the tickerplant so that everything is logged and order is maintained", and, of a table that takes inserts, updates and deletes, "The order in which logfile messages are replayed is hugely important in this case." [READ: KX, Data recovery for kdb+tick, https://code.kx.com/q/wp/data-recovery/; `tick/r.q`, https://raw.githubusercontent.com/KxSystems/kdb-tick/master/tick/r.q] The definition's table has neither half of that failure: its one operation is adding a row to a set, which gives the same set in any order and any number of times, so a replay needs no order and a second insert of an equal row is no error; and nothing outside the logs changes it. [INFER]

A raw layer kept by appending is the usual form. The bronze layer "Contains and maintains the raw state of the data source in its original formats", "Is appended incrementally and grows over time", and "Enables reprocessing and auditing by retaining all historical data"; cleansing and deduplication are the next layer's, made from it. [READ: Databricks, What is the medallion lakehouse architecture?, https://docs.databricks.com/aws/en/lakehouse/medallion] A store can enforce it: under Delta's `delta.appendOnly`, "New log entries MUST NOT change or remove data from the table." [READ: Delta Transaction Log Protocol, Append-only Tables, https://github.com/delta-io/delta/blob/master/PROTOCOL.md] Warehousing keeps every kind, raw, clean and corrections, and neither cleans nor selects; the table is a copy of the topics, whose values are already k-lines numbered by acquisition, not of the vendor's own form. [INFER]

**The options.**
- The table is written from the logs alone, by adding rows alone. It gives: the table equals `tableRows` at every moment, and a replay of the logs into an empty table gives it again. It costs: no row is fixed or removed by hand; a fix is a further record of a log (a correction).
- The table is also edited in place (a delete, a replaced row, a row from another program). It gives: repair in the store. It costs: the table is state no log reproduces; a replay differs from it, or fails as in kdb+; "every record" no longer follows from the logs.
- The store holds, beside the rows, facts that are no row (the position read, a time of writing, an annotation), in the table's own columns or apart. It gives: section 2's stored position, section 3's record time, section 4's coverage. It costs: each such fact is outside `Rows`, so the spec says of each what it is and that no row depends on it.

**What it gives the spec.** The objective rests on two things: the table is a function of the logs (`has_tableRows`, `table_rows`, theorems), and the consumer pushes every value (`consumer`, a requirement). [INFER] Within a working space the definition has by construction that only warehousing's pushes make a table, and only by adding rows: `Workspace.table` is of warehousing's logs alone ("Only warehousing writes into the database"); between working spaces it is a field, `Workspaces.tables_distinct` ("no table is written by two working spaces"). [READ: `lean/Workspace.lean`, `lean/Wiring.lean`] Of what is built it is a condition, to be verified there. [INFER] Whether the built store may hold anything that is not a row is a choice the spec states or leaves. [INFER] The table is rebuilt by replay only while the topics still hold their start (section 4). [INFER]

**Gaps.** None of its own; what bears on replay is in section 4.

## 2. What does delivery give, and what makes a sink idempotent?

**Kind:** engineering and modelling. **Bears on:** "A table is a set of rows" (Features); `consumer` (Requirements).

The three guarantees: "At most once" ("Messages may be lost but are never redelivered"), "At least once" ("Messages are never lost but may be redelivered"), "Exactly once" ("Each message is processed once and only once"); and "this breaks down into two problems: the durability guarantees for publishing a message and the guarantees when consuming a message." [READ: Apache Kafka 4.1 documentation, Design, Message Delivery Semantics, https://kafka.apache.org/41/design/design/]

The writer's side. A producer that retries may write a message twice; the idempotent producer "guarantees that resending will not result in duplicate entries in the log. To achieve this, the broker assigns each producer an ID and deduplicates messages using a sequence number that is sent by the producer along with every message." [READ: same] A duplicate in the log is the publisher's (acquisition's `publish…` say what each topic holds); warehousing copies what the log holds. [INFER]

The reader's side. A consumer that reads, saves its position, then processes gives at most once: "the process that took over processing would start at the saved position even though a few messages prior to that position had not been processed." One that reads, processes, then saves its position gives at least once: "when the new process takes over the first few messages it receives will already have been processed", and "In many cases messages have a primary key and so the updates are idempotent (receiving the same message twice just overwrites a record with another copy of itself)." "Kafka guarantees at-least-once delivery by default". [READ: Kafka, Design, Message Delivery Semantics]

Exactly once is given between Kafka's topics, not into a table. "The consumer's position is stored as a message in an internal topic, so we can write the offset to Kafka in the same transaction as the output topics receiving the processed data"; "it is only the producer which is transactional". [READ: Kafka, Design, Message Delivery Semantics; Using Transactions] The proposals that specify it give "the ability to write to several TopicPartitions atomically", the consumed offsets among the writes (KIP-98), and state that the "User needs to store transactional offsets inside Kafka group coordinator, not in any other external system for the sake of fencing" (KIP-447). [READ: KIP-98, Exactly Once Delivery and Transactional Messaging, https://cwiki.apache.org/confluence/display/KAFKA/KIP-98+-+Exactly+Once+Delivery+and+Transactional+Messaging; KIP-447, Producer scalability for exactly once semantics, https://cwiki.apache.org/confluence/display/KAFKA/KIP-447%3A+Producer+scalability+for+exactly+once+semantics] A consumer whose output is a database is outside it. [INFER]

Into an external system there are two documented ways. "When writing to an external system, the limitation is in the need to coordinate the consumer's position with what is actually stored as output. The classic way of achieving this would be to introduce a two-phase commit between the storage of the consumer position and the storage of the consumers output. This can be handled more simply and generally by letting the consumer store its offset in the same place as its output"; this pattern is followed for systems "which require these stronger semantics and for which the messages do not have a primary key to allow for deduplication." [READ: Kafka, Design, Message Delivery Semantics] "If the results of the consumption are being stored in a relational database, storing the offset in the database as well can allow committing both the results and offset in a single transaction", which gives "'exactly once' semantics that are stronger than the default 'at-least once' semantics you get with Kafka's offset commit functionality." [READ: Apache Kafka 4.1 Javadoc, KafkaConsumer, Storing Offsets Outside Kafka, https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html] So: a primary key, with writes that overwrite a row by a copy of itself; or, with no primary key, the position stored with the output in one transaction. [INFER]

A database sink of Kafka's connector ecosystem takes the first way. "This connector guarantees that records are delivered at least once from the Kafka topic." "The default insert.mode is insert. If it is configured as upsert, the connector will use upsert semantics rather than plain INSERT statements. Upsert semantics refer to atomically adding a new row or updating the existing row if there is a primary key constraint violation, which provides idempotence." The key is none by default, or taken from the record's key, from fields of its value, or from "Apache Kafka® coordinates" (topic, partition, offset). And "the source topic may also naturally contain multiple records over time with the same primary key, making upserts desirable": there an upsert replaces a row. [READ: Confluent, JDBC Sink Connector for Confluent Platform, https://docs.confluent.io/kafka-connectors/jdbc/current/sink-connector/overview.html; its configuration reference, `insert.mode`, `pk.mode`, `pk.fields`, https://docs.confluent.io/kafka-connectors/jdbc/current/sink-connector/sink_config_options.html]

The definition. `Rows`: "A row is in it or not: put there twice, it is there once." `Rows.has_ofLogs`: "The set holds a message of log `i` exactly when log `i` holds it, at some position." "a message one log pushes twice is one row, and a message two logs push is two" (`lean/Workspace.lean`). A topic of a working space has no key (`Kafka.Topic.ofName`: `Key := Empty`). [READ: `lean/Kahn/Rows.lean`, `lean/Workspace.lean`, `lean/Kafka.lean`] The model has no redelivery: its consumer is a process of the log. Under at-least-once delivery what a built consumer writes is not the log `consumer` gives, as a stretch is written again after later records; only the set of its rows can equal the definition's, and it does exactly when writing a row twice leaves it once and no write changes or removes another row. That is a key that is the row's identity, the log's mark and the value, neither coarser nor finer: under a coarser key a write replaces or drops another row; under a finer one an equal value is kept twice. [INFER]

The keys a sink can take, the record having none [INFER]:
- The mark and the whole value: the set's own identity. It costs a key over all seven fields of `KLine`, five of them `Float`; a database's equality of floats (a NaN, a signed zero) need not be equality of values, and the raw and the corrections topics may hold k-lines that break `finite`, only the clean series being filtered by `KLine.Keeps`.
- The mark and the value's `index`: the same rows as the set only where no two different values of one log have one `index`, which is acquisition's (`reader` with `publishRaw`, `cleaner` with `publishClean`, `publishCorrections`: position `n` of a topic holds `index` `n`), not warehousing's. Where it fails, an upsert that updates replaces a row and one that does nothing drops the second; the set holds both. To stay equal to the set the sink refuses or reports the conflict.
- Kafka's coordinates (topic, partition, offset): idempotent whatever the values. It puts the offset in the table, which `consumer` excludes ("the record's timestamp, its headers and its offset are not in the table"), and keeps two equal values at two offsets as two rows where the set has one.
- Under acquisition's requirements the values of one log are pairwise different, each holding its position, and the three give the same rows.

**The options.**
- A keyed write that leaves an equal row as it is, the position saved after the write. It gives: redelivery, and a replay from any earlier position into the same table, change nothing; no transaction joins the rows and the position. It costs: the choice of key above, and a key check on each write.
- The position stored with the rows in one transaction of the store, the rows inserted plainly. It gives: each record written once with no key, the documented way where messages have no primary key. It costs: a store with transactions; the position is a fact in the store that is no row (section 1); a replay from the start into a table not emptied doubles its rows.
- A plain insert with the position kept by Kafka. It gives at least once and no more: a failure between the write and the saving of the position writes rows twice, and the table is a multiset, not the definition's set.
- Kafka's transactions: they do not reach a table.

**What it gives the spec.** The feature "a table is a set of rows" is what makes at-least-once delivery enough: adding a row is idempotent, so the definition asks no exactly-once delivery of anything. [INFER] `consumer` is stated of a log and says nothing of delivery. [READ: `docs/designs/spec.md`] What is built is held at the table: after any redelivery, and any replay into the same table, it holds exactly the rows `table_rows` gives, which takes a write idempotent at the row's identity and a position saved no earlier than its rows; a stored position with plain inserts gives it under redelivery alone, a replay being then into a table emptied. [INFER] Which key, or the stored position, is a choice left; each key but the whole value equals the set only by acquisition's requirements, and the spec says so if it names one. [INFER]

**Gaps.** How a given database compares floats in a key was not examined. Kafka Connect's own support for exactly-once sinks, which the Design section points to, was not read.

## 3. How are corrections kept: one version or every version?

**Kind:** modelling. **Bears on:** "Keep in the database every record of acquisition's topics, of every kind" (Objectives); "a correction: a `KLine`: the bar as corrected, known by its `date`" (The data); `publishCorrections` (Acquisition).

The definition. The corrections are one of acquisition's three kinds (`Acquisition.Kind`), on a topic of their own, which holds what the publisher makes of the vendor's corrections alone (`Acquisition.corrections_topics`); warehousing reads all three (`Wiring.warehousingData`: `Topic := Acquisition.Kind`). [READ: `lean/Acquisition.lean`, `lean/Wiring.lean`] By the spec the corrections are "published as they come and applied to nothing", each "with its place among the corrections as its `index`", and "a correction is a bar: one that is no bar, a deletion say, has no form". [READ: `docs/designs/spec.md`] So in a table each correction is a row; two corrections of one `date` are two rows, their `index` differing; none replaces another, nor the raw bar of that date, which is a row of another log. A table has no current version: which correction of a date is the last is read from `index`. [INFER]

Bitemporal history. "Bitemporal history treats time as two dimensions: actual history records what history should be given perfect transmission of information, while record history captures how our knowledge of history changes"; the terms "valid, or effective (for actual) and transaction (for record)" name the same. "Actual history is no longer append-only, we go back and make retroactive changes. However record history itself is append only." "By layering an append-only record history over the actual history, we allow the actual history to be modified while creating a reliable history of its modifications." When it is needed: "Retroactive changes are a problem when actions are based on a past state that's retroactively changed"; "If we are merely recording a history, then we don't have to worry about it changing retroactively". Two ways to store it: "a bitemporal data structure" of record and actual ranges; or events, where "each event needs an actual date (or time) for when the event occurred in the world, and a record date (or time) for when we learned about it", a simpler structure of actual history alone being built from the events and kept "up to date as new events trickle in". Record time is the recorder's own: "Anything that can record a history will have its own record timestamps for when it learns information." [READ: Martin Fowler, Bitemporal History, https://martinfowler.com/articles/bitemporal-history.html; a secondary source, taken as background]

Market data keeps every version and reads the corrected one by default. A feed corrects by a further message: "The Broken Trade Message is sent whenever an execution on Nasdaq is broken", and "A trade break is final; once a trade is broken, it cannot be reinstated." [READ: Nasdaq TotalView-ITCH 5.0, 1.5.3, https://www.nasdaqtrader.com/content/technicalsupport/specifications/dataproducts/NQTVITCHspecification.pdf] A tick store "maintains a complete audit trail of all trade data including: Original trades, Corrected trades, Deleted trades, Metadata about when corrections occurred"; its plain read returns "only the corrected versions of trades", and a read as of a time the data before or after a correction. [READ: OneTick SQL documentation, Corrections and Time Travel, https://sql.docs.sol.onetick.com/corrections_and_time_travel.html] Both have a form for a record withdrawn (a break, a deleted trade); the corrections of a working space have none. [INFER]

Stores that replace rows version the whole table, and a version lasts while retention keeps it: "By default, write, append, and update operations will not remove the previous versions" in ArcticDB; "By default you can time travel to a Delta table up to 30 days old". [READ: ArcticDB documentation, Introduction, https://docs.arcticdb.io/latest/; Delta Lake documentation, Table batch reads and writes, Data retention, https://docs.delta.io/latest/delta-batch.html] A table that only gains rows needs none of it: each of its earlier states is the rows of a prefix of each of its logs. [INFER]

The mapping to the definition [INFER]:
- A correction's actual time is its `date`, the bar it is about. Its record time is its `index`, its place among the corrections: an order, not a date. The definition has no clock, and the record's `timestamp` (`Kafka.Record`) is not in the table. So a table holds the events of the second way of storing, each with an actual date and a record order.
- What a table answers: every correction of a date, in order; the bar of a date as known after the first `n` corrections (the correction of that date of greatest `index` below `n`, else the raw bar of that date); the latest, with `n` unbounded. Each is a view computed over the rows.
- What it does not: the order between logs. `Rows` keeps none, each `index` counts its own series, and Kafka keeps order within a partition only; whether correction `n` came before raw k-line `m` is nowhere. So "the series as known when k-line `m` was published", and "as known at time T", are not answered.
- Who needs record time: no part of a working space acts on a corrected state, the corrections being applied to nothing and the raw and clean topics not depending on them (`Acquisition.raw_topics`, `Acquisition.clean_topics`); the case in which bitemporal history is needed arises only for a reader of the table that applies the corrections, outside the working space.

**The options.**
- Every correction a row, and the latest of a date a view. It gives: every version, the as-known-after-`n` read, a table that only gains rows (sections 1 and 2 hold as they are), no retention of versions. It costs: the latest is a computation at each read, and its reader joins corrections to bars by `date`; no read by clock time.
- A record time kept with each row. It gives: the read as known at a time, and an order between logs as near as clocks give it. It costs: the row is no longer the value alone, against `consumer`; the time is Kafka's, the producer's or the broker's by the topic's `message.timestamp.type` ("Define whether the timestamp in the message is message create time or log append time", default `CreateTime`) [READ: Apache Kafka 4.1 documentation, Topic Configs, https://kafka.apache.org/41/configuration/topic-configs/], not the vendor's own; a time of writing into the store differs at each replay, so only the record's own timestamp keeps a rebuilt table equal.
- Only the latest of a date kept, the corrections applied in the store. It costs: a row replaced, which no process gives (the argument of `Kafka.compaction_not_process`: "No view that replaces a record already given is a process of the log"); a replay that depends on order; what was known before is lost; and it is against "applied to nothing" and "every record".
- Versions of the whole table, by number or snapshot. It is needed only where rows are replaced, and adds a retention policy for versions.

**What it gives the spec.** "Every record, of every kind" keeps every correction, each a row. [INFER] That every version and its order are in the table rests on two things already in the spec: a table only gains rows, and a correction's value holds its place as `index`. [INFER] The bar as corrected is a view over the rows, outside the table; whether the spec states that view is a choice. [INFER] Whether a row carries a record time is a choice, at the cost of the requirement's words "the row is the record's value". [INFER] Two limits stand whatever is chosen: a table gives no order between its logs, and a bar the vendor withdraws has no record. [INFER]

**Gaps.** No KX documentation on correcting ticks in kdb+ was found [SUMMARY]. ITCH and OneTick are of trades; how a vendor of bars publishes a corrected or a withdrawn bar was not researched.

## 4. How is a table replayed, and how can a store say what it covers?

**Kind:** engineering. **Bears on:** "that each reader reads it from its start, that retention removes no record before it is read" (Order, how what is built is verified); "a topic is its whole log, never compacted" (What it guarantees).

The definition. "A topic is seen as its log: everything ever appended to it. What retention or compaction leave readable is a view of that log, not the log itself: no process gives that view (`compaction_not_process`). That a reader reads the whole log is assumed here, not proved: it holds where retention and compaction remove no record before the reader has read it." `Rows` has `has` alone, and a table's row is a message marked with its log (`Workspace.TableRow`): a table says which rows it holds and of which log each is, and nothing of how much of a log was read, nor of a log that has pushed no row. [READ: `lean/Kafka.lean`, `lean/Kahn/Rows.lean`, `lean/Workspace.lean`] In the definition a table at a stage is the rows of the prefixes read so far, and all of them in the limit; there is no stage at which it is complete. [INFER]

Kafka removes records by age and size, never by what was read. `cleanup.policy`: "The "delete" policy (which is the default) will discard old segments when their retention time or size limit has been reached. The "compact" policy will enable log compaction, which retains the latest value for each key." `retention.ms`: "This configuration controls the maximum time we will retain a log before we will discard old log segments to free up space if we are using the "delete" retention policy. This represents an SLA on how soon consumers must read their data. If set to -1, no time limit is applied"; its default is 604800000 (7 days). `retention.bytes`: "By default there is no size limit only a time limit"; its default is -1. `segment.bytes`: "Retention and cleaning is always done a file at a time". [READ: Apache Kafka 4.1 documentation, Topic Configs, https://kafka.apache.org/41/configuration/topic-configs/] The broker holds no state of what was consumed: "the position of a consumer in each partition is just a single integer", kept for the consumer, where other systems have the broker know "what is consumed" so that "it can immediately delete it". [READ: Kafka, Design, Consumer Position, https://kafka.apache.org/41/design/design/] So "retention removes no record before it is read" is not a setting of Kafka's: it is met by no limit at all (`retention.ms` and `retention.bytes` of -1, `cleanup.policy` of `delete` alone), or by a limit every reader is known to stay within; by default a record is discarded with its segment once the seven days' limit is reached, read or not. [INFER]

A reader whose position is gone is moved, by default without an error. `auto.offset.reset`: "What to do when there is no initial offset in Kafka or if the current offset does not exist any more on the server (e.g. because that data has been deleted)": `earliest`, `latest`, `by_duration`, or `none`, "throw exception to the consumer if no previous offset is found for the consumer's group"; the default is `latest`. [READ: Apache Kafka 4.1 documentation, Consumer Configs, https://kafka.apache.org/41/configuration/consumer-configs/] `OffsetOutOfRangeException`: "No reset policy has been defined, and the offsets for these partitions are either larger or smaller than the range of offsets the server has for the given partition." [READ: Apache Kafka 4.1 Javadoc, https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/OffsetOutOfRangeException.html] So by default a new reader starts at the end, not the start; with `earliest` it starts at the first record still kept, and a reader whose position was removed goes on from there, the removed stretch passed over in silence; only with no reset policy is the loss an error. [INFER]

Offsets do not count records; `index` does. "Note that offsets are not guaranteed to be consecutive (such as compacted topic or when records have been produced using transactions)." A partition's two ends are known from outside the topic: `beginningOffsets`, "Get the first offset for the given partitions", and `endOffsets`, "the end offset is the high watermark (that is, the offset of the last successfully replicated message plus one)". [READ: Apache Kafka 4.1 Javadoc, KafkaConsumer, https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html] In the definition "A record's position in its log stands for its offset: Kafka's offsets can skip numbers, but their order is the same" (`lean/Kafka.lean`). The spec's check, "at each position `n` of an acquisition topic a reader finds the k-line of index `n`", is one any reader makes from the values alone: a reader that has read `n` records and finds an `index` other than `n` has lost records, or the publisher has broken its requirement, whatever the reset policy. [INFER]

Coverage is kept as intervals beside the data, or as a sequence in the stream. A catalog keeps "Closed-interval set operations used by the parquet catalog for coverage and gap analysis", finds "the parts of a query interval that are not covered by existing data intervals", and tells empty from not covered: "Successful empty responses can extend known-empty coverage", while a batch is not written back where its "source coverage intervals are unknown". [READ: NautilusTrader, `crates/persistence/src/backend/parquet/intervals.rs` and `docs/concepts/data/catalog.md`, https://github.com/nautechsystems/nautilus_trader/tree/c3bde0c1b8d1b120c78146b7923ea266323234ba] A feed numbers its messages: each packet holds "The sequence number of the first message in the packet" and a count; "Heartbeats are sent periodically by the server so receivers can sense packet loss even during times of low traffic", and "contain the next expected Sequence Number"; at the end of a session, "This is the last chance to ensure that all messages have been received." [READ: Nasdaq, MoldUDP64 Protocol Specification V 1.00, https://www.nasdaqtrader.com/content/technicalsupport/specifications/dataproducts/moldudp64.pdf]

In a working space's data [INFER]:
- `index` is the sequence number. A table's rows of a log hold its first `n` records exactly when they hold a row of each `index` from 0 to `n − 1`; with no row of a greater `index`, they are that log's rows at the stage `n`.
- A hole is always a loss. An `index` absent below a greater one held is a record lost, never a bar the market or the cleaner left out: such a bar takes no `index`, the numbering being by place. So no record of a gap is needed.
- The tail is not in the rows. Whether records follow the greatest `index` held is not shown; the topics carry `KLine` alone, so no heartbeat and no end mark; Kafka's end offset says it from outside, of one moment.
- All of it rests on acquisition's requirements (position `n` holds `index` `n`), which are the spec's.

**The options.**
- No limit of retention on the topics. It gives: any reader, whenever it starts, reads from position 0, and a table is rebuilt by replay at any time. It costs: storage that grows with the series; a setting that holds only while nobody changes it, verified on what is built.
- A limit longer than every reader's delay. It gives: bounded storage. It costs: a reader that starts after the limit (a new table, a new chart, an engine added) no longer reads from the start; the table is the only copy of what was removed, and its rebuilding is a reset from the vendor, outside the working space; every reader's delay is watched.
- Coverage read from the rows: per log, the length of the prefix held, by the contiguous `index`. It gives: a hole found by a query, with no field added. It costs: the tail unknown.
- Coverage recorded beside the table: per log, the count or the offset read to. It gives: the tail, against the log's end offset. It costs: a fact in the store that is no row (section 1), and one that can disagree with the rows.
- An end mark or a heartbeat in the topic. It gives: the tail in the stream. It costs: a message that is no `KLine`, against "Each of acquisition's topics carries market's `KLine` alone"; a heartbeat needs a clock, which the definition has not; a series still going has no end.
- The reader's policy when its position is gone: an error, or the earliest record kept. With the second the loss is seen by the `index` check alone.

**What it gives the spec.** "Retention removes no record before it is read" is a condition on the built topic's configuration, which Kafka does not give by default (seven days) and cannot express as such, its retention knowing no reader; with readers that may start at any time it comes to no limit, and the spec says which it asks. [INFER] "Each reader reads it from its start" is likewise a condition on the built reader, the default being the end. [INFER] The check that position `n` holds `index` `n` detects a removed or skipped stretch from the values alone, given acquisition's requirements, where offsets do not. [INFER] What a table covers is, for each of its logs, a prefix, read from `index`; `Rows` has no coverage and no stage is complete, so a claim that a table is complete is a claim about the log's end at a moment, outside the table. [INFER] Left as choices: the retention, and whether coverage is read from the rows or recorded. [INFER]

**Gaps.** How the age of a segment is reckoned for `retention.ms` was not read in place. That an out-of-range position throws under `auto.offset.reset` of `none` is read from the configuration's and the exception's texts together, not from one statement. Tiered storage, and retention in brokers other than Kafka, were not studied.
