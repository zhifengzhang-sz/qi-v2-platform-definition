# Decisions

Each decision once: its date, who decided (the owner, or the session as a proposal until the owner decides), the decision, why, and the documents it shapes. A decision still open is under Open, with the proposal.

- **2026-11-10, the owner.** The platform is defined on Kahn process networks: data is logs, the system's input and output; a component is a process, a function from its input logs to its output logs that never takes back output it has given; a platform is a network of components wired by the topics; the system is one function from the input logs to the output logs. Why: "the system is a map (in function sense) on the data". Shapes: `lean/Kahn/`, `lean/Workspace.lean`.
- **2026-11-10, the owner.** The Lean is a definition, not code to run: it is checked by its proofs, and `noncomputable` where the limit of logs needs it. Why: each component's code is written in its own project; the definition is what that code must satisfy. Shapes: `lean/`, `docs/acquisition.md`.
- **2026-11-10, the owner.** Every claim is proved from the base up. Why: a claim the logic does not force is a choice, and is named as one. Shapes: `lean/`, `agents/rules.md`.
- **2026-11-10, the owner; its reading that the contracts are the shape alone overturned, 2026-11-19, the owner.** The definitions give the shape and the contracts (the API). The shape is what each part reads and writes; the contracts are not that alone, but each contract's records and rules, which the definition holds (2026-11-19, the definition's two parts). Whether a part is a plugin is the implementation's, not the definition's. Shapes: `lean/Acquisition.lean`, `lean/Warehousing.lean`, `docs/acquisition.md`, `docs/designs/contracts-and-specs.md`.
- **2026-11-10, the owner.** Kafka's internals (replication, brokers) are taken as given. A topic has Kafka's shape, the same for every topic: one log of records for each partition, everything ever appended to it; what retention or compaction leave readable is a view of it. Why: Kafka's shape is well defined; and a view that replaces a record already given is not a process (`Kafka.compaction_not_process`). Shapes: `lean/Kafka.lean`.
- **2026-11-10, the session, the owner leaving it.** A topic's schema is its key and value types; a Lean type carries its fields' names, so nothing beyond the types is needed. Two topics with the same types have the same schema, and the warehouse consumer is the same for both, which is what "based on the topic schema" says. Shapes: `lean/Kafka.lean`, `lean/Warehousing.lean`.
- **2026-11-10, the owner.** The four components are acquisition, warehousing, visualization and the market model engine (optional), wired by the topics only. Acquisition is the one component that reads the system's input logs, the vendor's; the others read Kafka's topics alone. Shapes: `lean/Workspace.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** Each Kafka topic has one writer and any number of readers, and each table of the database one working space: no two topics have the same name, only warehousing writes into the database, and no table is written by two working spaces. Why: two writers into one log merge by arrival (`Kahn.no_arrival_merge`), which is a topic's reason, each partition of it being a log; for a table it is a choice (the decision on what a table is). A topic or a table is known by its name, so distinct names make it hold for Kafka's topics and the database's tables, not only for the definition's. Shapes: `lean/Workspace.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** A working space has one acquisition; several working spaces may work side by side, one for each acquisition (one for Massive, one for Yahoo, say), each with its own warehousing, engine and visualization. Why: one acquisition to a working space keeps each working space simple; working side by side, they keep each topic's one writer and each table's one working space. Shapes: `lean/Workspace.lean` (`Workspaces`), `lean/Wiring.lean`, `lean/Acquisition.lean`.
- **2026-11-10, the owner.** Acquisition: each k-line contract defines one, composed of the reader, the cleaner and the publisher. Raw, corrected raw and clean k-lines are all the contract's k-line. The cleaner maps the raw series to the clean series; the publisher publishes the raw and clean series and the vendor's corrections; topic details are not acquisition's business. Cleaning happens in acquisition, not in warehousing. Shapes: `lean/Acquisition.lean`, `docs/acquisition.md`.
- **2026-11-10, the owner.** Acquisition makes no corrected raw series and has no reset: a reset is outside the working space, and within one nothing starts again. The raw series has two parts: first the vendor's corrected raw series, as a reset reads it, then the vendor's raw series, appended to it. The clean series is made from the raw series. The vendor's corrections are published as they come and applied to nothing, so the raw and clean topics do not depend on them (`Acquisition.clean_topics`): a correction made after a working space started shows in its corrections topics alone. Why: the reset's logic is too complicated for the working space. Shapes: `lean/Acquisition.lean`, `lean/Wiring.lean`, `docs/acquisition.md`.
- **2026-11-10, the owner.** The reader reads both parts of the raw series; how (a replayer in it, say) is the implementation's, not the definition's, and so is the switch from the first part to the second, by the reader's own state. In the Lean (the session's, from the base): the source is one log, what the reader reads in the order it reads it, and the reader one process of it; that the source holds the corrected raw series first is a modelling choice, not a theorem. Why one log: a process is a function of its logs, so of two logs side by side it cannot put one after the other, not knowing where the first ends; the order the reader reads in is data, in the one log. Shapes: `lean/Acquisition.lean`, `docs/acquisition.md`.
- **2026-11-10, the session, the owner leaving it; the three kinds are the owner's.** Each of acquisition's topics carries one kind of data (raw, clean, corrections), and the publisher is three parts, one for each kind, each writing the topics of its kind alone, from its own series alone (`Acquisition.clean_topics`). Shapes: `lean/Acquisition.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** The clean topics are what visualization and the market model engine read; warehousing reads all of acquisition's topics, of every kind, and pushes them all into the database. The consumer reads one partition at a time; what it pushes is left open. Why the one partition (the session's, from the base): reading a topic's partitions into one log as they arrive would be a merge by arrival. Shapes: `lean/Wiring.lean`, `lean/Warehousing.lean`, `lean/Visualization.lean`.
- **2026-11-10, the owner.** Visualization is a pure consumer: it reads only from Kafka, the clean topics and, when the market model engine is there, the engine's topics; it gives nothing in the Kafka sense, and displays the chart in an HTML page. Shapes: `lean/Visualization.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner; its messages, 2026-11-19, the owner.** The market model engine is optional, a worker: it reads the clean topics and publishes topics of its own, whose messages are the chanlun contract's records, which the definition holds (2026-11-19, the definition's two parts); the definition names no release of the contract, which takes its records from the definition. A working space may lack it, as the product of the platform's own project does; without it, the chart is drawn from the clean topics alone (`Wiring.chart_without_engine`). Shapes: `lean/MarketModelEngine.lean`, `lean/Wiring.lean`, `docs/designs/contracts-and-specs.md`.
- **2026-11-10, the owner.** The definition is a project of its own, public, following the practices of every qi-v2 project (`qi-v2-nix`'s `practices.md`). Why: every project of the platform is rebuilt against it, so it is versioned and pinned by its own tag. Shapes: `flake.nix`, `Makefile`, `PRODUCTS.md`, `agents/`, `docs/`.
- **2026-11-10, the owner.** A table of the database is a set of rows: it holds the rows of every log warehousing pushes into it, in no order (`Workspace.tableRows`). So one table takes every partition of a topic, and may take several topics: several logs into one set of rows is a process (`Kahn.Rows.ofLogs`). One working space to a table is then a choice, by which what a table holds is defined within one working space; it does not rest on merging by arrival, as one writer to a topic does. In the Lean (the session's, both modelling choices): a row is a message marked with the log it is from, the logs' messages being of different types, so that a message one log pushes twice is one row, and a message two logs push is two. Why: a table keeps no order, so nothing is merged by arrival. Shapes: `lean/Kahn/Rows.lean`, `lean/Workspace.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner; overturned, 2026-11-19, the owner (the component specs, below).** As it stood: the definition holds each part to its shape: what it reads and writes, and Kahn's condition. What a part gives is the implementation's: any process of the part's type is one, one that gives nothing among them, and that the topics of a kind hold their series is not a theorem. Why: the definitions give the shape and the contracts; what a part does is the implementation's. A condition that a series can be read back from its topics was considered and left: a series is one log, in order, and Kafka keeps order within one partition only, so a publisher would have to write the order into its records. What replaces it: each part is held to its spec, and a series is read back from its topics by each k-line's `index`, its place in its series (`docs/designs/contracts-and-specs.md`, Reading a series back from its topics). Shapes: `lean/Acquisition.lean`, `docs/acquisition.md`.
- **2026-11-12, the owner; how `type` and `uses` are read, the session's, in the plan the owner approved on 2026-11-15.** What each product of the platform must give is read from the definition itself, never from text written elsewhere: each release gives an export of the definition's open parts, `export/parts.json`, made by Lean from the definition and checked by the project's own make to be what Lean gives, one entry for every field of every structure the definition declares, with its name, its structure, its type, its doc comment and the other parts its type uses (its form: `README.md`, The open parts). Why: a product reads what it must give from the definition, so the definition gives it in a form its users can read. Shapes: `dev/parts.lean`, `dev/parts-check.py`, `export/parts.json`, `Makefile`, `flake.nix`, `README.md`, `PRODUCTS.md`, `docs/process.md`.
- **2026-11-19, the owner.** The definition has two parts: the component specs, each component's objectives, requirements and features; and the contract specs, the formal definition of each contract, its records and its rules. The definition holds the formal definition of each contract, and the contracts take it from the definition at a release. Why: a definition that leaves the data open is too loose to be useful: any type fills an open part, so no contract is checked against it. Shapes: `docs/designs/contracts-and-specs.md`, `lean/`, `PRODUCTS.md`.
- **2026-11-19, the owner.** The component specs: a component is held to what it must do, its objectives, requirements and features being in the definition, and not to what it reads and writes alone. Why: held to its shape alone, any process of a component's type is one, one that gives nothing among them. It overturns the decision of 2026-11-10 that the definition holds each part to its shape. Shapes: `docs/designs/contracts-and-specs.md`, `lean/Acquisition.lean`, `lean/Warehousing.lean`, `lean/MarketModelEngine.lean`, `lean/Visualization.lean`, `lean/Wiring.lean`, `docs/acquisition.md`.

## Open

Each a proposal of the session's, 2026-11-19, until the owner decides; the design is `docs/designs/contracts-and-specs.md`.

- **What the definition holds of each contract.** The proposal: each contract's records, its rules, its `Rule` and `broken`, and chanlun's theorem `MergedBar.startNotAfterEnd`, in name and meaning as the contract's Lean states them, in `lean/Market.lean` and `lean/Chanlun.lean`; the `.proto`, the reader of Protobuf's JSON (`ProtoJson`, the `FromJson` instances), the examples and the program that checks them, Go and TypeScript stay the contracts' project's. Why: the records and the rules are the contract's formal definition; the reader and the examples' check are code to run, and on the wire a record is read and written by code a standard library generates from the `.proto`. Shapes: `docs/designs/contracts-and-specs.md` (The contract specs), `lean/Market.lean`, `lean/Chanlun.lean`.
- **The k-line and the engine's messages.** The proposal: the k-line, raw, corrected raw and clean, is market's `KLine`; each of the engine's topics carries one of chanlun's six records; market's `OngoingKLine` is held with its contract and carried by no topic. It rewrites the decision of 2026-11-10 on acquisition (each k-line contract defines one): market's defines it. Why: the definition holds two contracts, and these are their records; acquisition's three kinds carry complete k-lines. Shapes: `docs/designs/contracts-and-specs.md` (The data the definition left open), `lean/Acquisition.lean`, `lean/MarketModelEngine.lean`.
- **The input logs.** The proposal: the source and the vendor's corrections are logs of market's `KLine`, the source the vendor's k-lines, its corrected raw series first, and a correction the bar as corrected, known by its `date`; the vendor's own form is read into k-lines before the system's input. The other way: the vendor's own record, with its reading into k-lines a part of acquisition's data. Why: every message of the system is then a contract's record, where a vendor's own form is the vendor's, which no contract of the platform states. Shapes: `docs/designs/contracts-and-specs.md` (The data the definition left open), `lean/Acquisition.lean`, `lean/Wiring.lean`.
- **No key.** The proposal: no topic of a working space has a key (`Empty`), and every record written has a value. Why: no part reads a key: a topic is its whole log, never compacted (`Kafka.compaction_not_process`), and which partition a record goes to is the writer's choice. Shapes: `docs/designs/contracts-and-specs.md`, `lean/Kafka.lean`.
- **What warehousing pushes.** The proposal: what the consumer pushes for a record is its value, the row the record's value by the topic's schema. It rewrites the decision of 2026-11-10 on the clean topics (what it pushes is left open). Why: a topic's schema is its key and value types, and no record has a key. Shapes: `docs/designs/contracts-and-specs.md` (Warehousing), `lean/Warehousing.lean`, `lean/Wiring.lean`.
- **What visualization gives.** The proposal: one log for each partition of each topic it reads, each the values of that partition's records; the chart on the page is the set of their rows. Why: one log of several topics' records would merge by arrival (`Kahn.no_arrival_merge`), so no process with one log shows every record it reads. Shapes: `docs/designs/contracts-and-specs.md` (Visualization), `lean/Visualization.lean`, `lean/Wiring.lean`.
- **The components' requirements.** The proposal: each component's requirements as `docs/designs/contracts-and-specs.md` gives them, among them: the cleaner keeps, in order, each k-line that breaks none of market's rules and whose date is after every kept one's, and repairs none; the engine's records keep their rules, name only k-lines it has read and merged bars it has written, and put each k-line it reads that keeps market's rules in a merged bar. Not required: that the engine's records are right by 缠论's lessons, which no contract states. Why: each is what the record says the component is for, stated so that a component that gives nothing meets none. Shapes: `docs/designs/contracts-and-specs.md` (The component specs), the components' files of `lean/`, `docs/acquisition.md`.
