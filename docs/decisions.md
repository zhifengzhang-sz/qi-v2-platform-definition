# Decisions

Each decision once: its date, who decided (the owner, or the session as a proposal until the owner decides), the decision, why, and the documents it shapes. A decision still open is under Open, with the proposal.

- **2026-11-10, the owner.** The platform is defined on Kahn process networks: data is logs, the system's input and output; a component is a process, a function from its input logs to its output logs that never takes back output it has given; a platform is a network of components wired by the topics; the system is one function from the input logs to the output logs. Why: "the system is a map (in function sense) on the data". Shapes: `lean/Kahn/`, `lean/Workspace.lean`.
- **2026-11-10, the owner.** The Lean is a definition, not code to run: it is checked by its proofs, and `noncomputable` where the limit of logs needs it. Why: each component's code is written in its own project; the definition is what that code must satisfy. Shapes: `lean/`, `docs/acquisition.md`.
- **2026-11-10, the owner.** Every claim is proved from the base up. Why: a claim the logic does not force is a choice, and is named as one. Shapes: `lean/`, `agents/rules.md`.
- **2026-11-10, the owner.** The definitions give the shape and the contracts (the API): what each part reads and writes. Whether a part is a plugin is the implementation's, not the definition's. Shapes: `lean/Acquisition.lean`, `lean/Warehousing.lean`, `docs/acquisition.md`.
- **2026-11-10, the owner.** Kafka's internals (replication, brokers) are taken as given. A topic has Kafka's shape, the same for every topic: one log of records for each partition, everything ever appended to it; what retention or compaction leave readable is a view of it. Why: Kafka's shape is well defined; and a view that replaces a record already given is not a process (`Kafka.compaction_not_process`). Shapes: `lean/Kafka.lean`.
- **2026-11-10, the session, the owner leaving it.** A topic's schema is its key and value types; a Lean type carries its fields' names, so nothing beyond the types is needed. Two topics with the same types have the same schema, and the warehouse consumer is the same for both, which is what "based on the topic schema" says. Shapes: `lean/Kafka.lean`, `lean/Warehousing.lean`.
- **2026-11-10, the owner.** The four components are acquisition, warehousing, visualization and the market model engine (optional), wired by the topics only. Acquisition is the one component that reads the system's input logs, the vendor's; the others read Kafka's topics alone. Shapes: `lean/Workspace.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** Each Kafka topic has one writer and any number of readers, and each table of the database one writer: no two topics have the same name, only warehousing writes into the database, and no table is written by two working spaces. Why: two writers into one log merge by arrival (`Kahn.no_arrival_merge`); a topic or a table is known by its name, so distinct names make one writer hold for Kafka's topics and the database's tables, not only for the definition's. Shapes: `lean/Workspace.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** A working space has one acquisition; several working spaces may work side by side, one for each acquisition (one for Massive, one for Yahoo, say), each with its own warehousing, engine and visualization. Why: one acquisition to a working space keeps each working space simple; working side by side, they keep each topic's and each table's one writer. Shapes: `lean/Workspace.lean` (`Workspaces`), `lean/Wiring.lean`, `lean/Acquisition.lean`.
- **2026-11-10, the owner.** Acquisition: each k-line contract defines one, composed of the reader, the cleaner and the publisher. Raw, corrected raw and clean k-lines are all the contract's k-line. Corrections (the vendor's corrections stream) and raw give corrected raw, by a step left unspecified; the cleaner maps the corrected raw series to the clean series; the publisher publishes the raw, corrected raw and clean series and the vendor's corrections; topic details are not acquisition's business. Cleaning happens in acquisition, not in warehousing. Shapes: `lean/Acquisition.lean`, `docs/acquisition.md`.
- **2026-11-10, the owner, on the session's proposal.** Nothing published is taken back, so a correction is added, never applied in place. The corrected raw series is a log of revisions: a k-line's first version, then each corrected version as a message of its own; the k-line as it stands now is a view. The clean series may start again: a reset is a message of the clean series, and what follows it is the clean series made again; the clean series as it stands, the k-lines since the last reset, is a view (`Acquisition.Clean.sinceReset_not_process`). Why: the earlier design's reset deleted the clean topic and published it again, which takes back output, and no process does that. Shapes: `lean/Acquisition.lean`, `docs/acquisition.md`.
- **2026-11-10, the owner.** Acquisition has two readers: the vendor's (a feed, a file or a database), and the reset's. A reset is a replay: the reset's reader reads the history again from its start, the clean series is made again from it, and when the replay is over the vendor's series takes over. When a reset comes, when the replay is over and the switch are acquisition's own state, the implementation's, not the definition's. What the history is (a file, a database, or acquisition's own topics read back) is left open. Shapes: `lean/Acquisition.lean`, `lean/Wiring.lean`, `docs/acquisition.md`.
- **2026-11-10, the session, the owner leaving it.** Each of acquisition's topics carries one kind of data (raw, corrected raw, clean, corrections), and the publisher is four parts, one for each kind, each writing the topics of its kind alone; so the clean topics hold the clean series alone (`Acquisition.clean_topics`). Shapes: `lean/Acquisition.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** The clean topics are what visualization and the market model engine read; warehousing reads all of acquisition's topics, of every kind, and pushes them all into the database. The consumer reads one partition at a time; what it pushes is left open. Why the one partition (the session's, from the base): reading a topic's partitions into one log as they arrive would be a merge by arrival. Shapes: `lean/Wiring.lean`, `lean/Warehousing.lean`, `lean/Visualization.lean`.
- **2026-11-10, the owner.** Visualization is a pure consumer: it reads only from Kafka, the clean topics and, when the market model engine is there, the engine's topics; it gives nothing in the Kafka sense, and displays the chart in an HTML page. Shapes: `lean/Visualization.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** The market model engine is optional, a worker: it reads the clean topics and publishes topics of its own, whose messages derive from the chanlun contract 3.1.0. A working space may lack it, as the product of the platform's own project does; without it, the chart is drawn from the clean topics alone (`Wiring.chart_without_engine`). Shapes: `lean/MarketModelEngine.lean`, `lean/Wiring.lean`.
- **2026-11-10, the owner.** The definition is a project of its own, public, following the practices of every qi-v2 project (`qi-v2-nix`'s `practices.md`). Why: every project of the platform is rebuilt against it, so it is versioned and pinned by its own tag. Shapes: `flake.nix`, `Makefile`, `PRODUCTS.md`, `agents/`, `docs/`.

## Open

1. **What a reader of a clean topic does at a reset.** It sees the reset, a message like any other; that it starts again is not yet in the definition. Proposal: a construction in the base that runs a process afresh after each reset (the process on the k-lines since the last reset, its output starting again with a reset of its own), with the theorem that it is a process; the engine's worker and visualization's chart are made with it, so a reset in the clean topics is a reset in the engine's topics and in the chart.
